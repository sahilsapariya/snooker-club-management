## Verdict

**A receptionist can run a full shift in this app today. An owner cannot set the club up in it.**

Everything from "sign in" through "reconcile the till" works end to end and is covered by tests. The billing engine, session lifecycle, payments, expenses, cash closing and reporting are all built, wired and verified against the real database.

The gap is **onboarding**. There is no screen anywhere that creates a club, adds a physical table, or adds a member of staff. Those three things currently require SQL. Everything else missing is comparatively minor.

> **The single most important finding:** a brand-new club cannot be made usable from inside the app. Tables have no management UI at all, staff invites exist as an API function that no screen calls, and the platform admin screens are read-only. All three have working database support already — this is missing UI, not missing foundations.

## Club staff screens

Five tabs — **Tables, Sessions, Cash, Alerts, More** — plus three screens reached from More. The tab bar holds only what a receptionist touches during a shift, so every target stays big enough to hit one-handed at a counter.

### Tables — `(tenant)/tables` · 171 lines · Done

The floor. Landing screen and the entry point to everything operational.

```
┌──────────────────────────┐
│ Reception          (SS)  │
│ Royal Snooker Club       │
│ [2 in play][3 free][1 ⚠] │
├──────────────────────────┤
│ ▌Snooker 1      In play  │
│  Snooker · No. 1         │
│  ┌────────────────────┐  │
│  │⏱ 00:42:07  ₹40.00 │  │
│  └────────────────────┘  │
├──────────────────────────┤
│ ▌Pool 2     Maintenance  │
│  🔧 Cloth being replaced │
└──────────────────────────┘
```

**Works**

- Card per table: name, type, number, status badge, colour accent encoding state
- Occupied tables show a live clock counting from the recorded start, plus running total
- Clock keeps counting past the booked time — the badge changes to "Time up", nothing ends
- Tap a free table → start-session sheet; tap an occupied one → session sheet
- Summary chips, pull-to-refresh, empty state that differs for owner vs reception
- Background watcher flips sessions to `TIME_COMPLETED` and raises a local notification

**Missing**

- No way to add, rename, reorder or deactivate a table

│  Lemon Soda 3 × ₹35  🗑  │
│ PAYMENT                  │

**Works**

**Missing**

- Quantity of an existing line cannot be edited — only removed and re-added
- Frames played cannot be entered, so frame billing is unreachable from the UI
- No receipt to print or share

### Cash — `(tenant)/cash` · 364 lines · Done

The end-of-day flow: what came in, what went out, and whether the drawer agrees.

```
┌──────────────────────────┐
│ Trading day              │
│ 21 Aug 2026              │
│ TODAY'S TAKINGS          │
│  Cash           ₹400.00  │
│  Card, UPI…     ₹  0.00  │
│  Total received ₹400.00  │
│  Still owed     ₹500.00  │
│ TODAY'S EXPENSES [Record]│
│  🧾 Cleaning    ₹500.00  │
│ CASH DRAWER              │
│  Opening float  ₹2000.00 │
│  Cash taken     ₹ 400.00 │
│  Cash spent    -₹ 500.00 │
│  Expected      ₹1900.00  │
│  Count  ₹ [   1850.00 ]  │
│  Short by 50.00          │
│ [ Close till for today ] │
└──────────────────────────┘
```

**Works**

- Uses the club's **trading day**, not the device's calendar day — a club open past midnight is still on yesterday's books
- Takings split by payment method, because only cash affects the drawer
- Outstanding customer debt surfaced separately from takings
- Today's expenses inline, with a record-expense sheet
- Open the till with a counted float; close it with a counted drawer
- Expected and difference are **generated columns** — a discrepancy cannot be papered over from the app
- Live short/over feedback as you type the count

**Missing**

- Yesterday's closings are not viewable — `useRecentClosings` exists but no screen uses it
- Expenses cannot be edited or deleted from the UI
- Cannot reconcile a day other than today

**Works**

- All six queries run in parallel — the screen is as slow as the slowest, not the sum

**Missing**

- No export (CSV, PDF or share)
- No custom date range, only the four presets
- Visible to receptionists as well as owners — consistent with RLS on the underlying tables, but worth a decision

## Data & security

20 tables, 3 views, 12 client-callable functions, 73 RLS policies, 14 ordered migrations. The mobile app is treated as hostile throughout.

### Four independent isolation layers

| Layer                      | What it does                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Row Level Security         | All 20 tables. Policies written in terms of `SECURITY DEFINER` helpers in a non-exposed `app` schema, so no policy recurses into the table it protects |
| Composite foreign keys     | `(tenant_id, parent_id)` against `unique (tenant_id, id)` — a row structurally cannot reference another club's row, even if a policy is wrong          |
| Grants                     | `anon` holds nothing. `authenticated` gets exactly CRUD — Supabase's stock defaults also hand out `TRUNCATE`, which ignores RLS, and that is stripped  |
| No write path to `tenants` | Not for club staff, and not for the platform admin either. Branding changes go through SECURITY DEFINER RPCs that re-check authority                   |

### Structural guarantees

- `sessions.actual_duration_seconds` is a generated column — no client, service role or migration can write it. Attempting it raises `428C9`
- An open session structurally cannot carry an end time; a closed one must. "Time up" is an open state
- A partial unique index allows one open session per table
- Session item prices are snapshotted and made immutable by trigger — yesterday's bill can't move
- Stock is an append-only ledger; `products.stock_quantity` is a trigger-maintained projection
- Cash `expected` and `difference` are generated — a discrepancy can't be hidden from the app
- `business_date` is always derived server-side from the club's timezone and trading-day cutoff; a supplied value is discarded
- Money is integer minor units in `bigint` throughout — never float, never `numeric`

### Reporting security

All five report functions and `daily_cash_summary` are `SECURITY INVOKER`. They take a `tenant_id` argument, but that argument is not the security boundary — RLS is. A `DEFINER` function here would total another club's takings for anyone who passed a different id.

Verified live: a Royal owner's report returns 5 sessions and ₹1,500 for their own club and zeros for Blue Cue, which genuinely has 5 closed sessions in the same range.

## Findings

Ranked by what actually blocks using the product. All verified against the codebase, not recalled.

### 1. A club cannot be set up from inside the app — **blocking**

Three separate holes compound into one: no club can be created, no table can be added, and no staff member can be invited. Onboarding a real club today means writing SQL.

Every piece of supporting machinery exists and is tested — the RPCs, the typed client functions, the React hooks. Only the forms are missing. This is the highest-value work remaining and probably the smallest relative to its impact.

### 2. Sixteen built functions are never called — **dead surface**

`useCreateTenant`, `useUpdateTenantBranding`, `useSetTenantStatus`, `addTenantMember`, `useUpdateBillingSettings`, `useRecentClosings`, `useDeleteExpense`, `useUpdateSessionItem`, `useLowStockProducts`, `fetchStockHistory`, `sendPasswordReset` and others are exported, typed and unreachable.

This isn't waste so much as a map of the UI backlog — each one is a feature that stops at the data layer. Worth tracking deliberately rather than letting it drift. (`resolvePricingRule` and `requestPushPermission` were flagged initially but verified as used internally.)

### 3. The audit log is never written by the app — **partial**

`activity_logs` is modelled, RLS-protected and append-only — but only the four platform RPCs ever insert into it. Sessions starting, payments taken, prices changed and stock adjusted leave no audit entry.

For a product handling a club's money, this is the finding to fix second. It's cheap: one helper called from the existing mutation hooks.

### 4. Notifications are modelled but almost never raised

Seven event types exist with rendering, and the inbox works. Only `SESSION_TIME_COMPLETED` fires, and only as a local device notification while the app is open. Low stock, payment received and cash-closing reminders never appear.

Push delivery is a separate, larger piece — it needs a server-side worker holding an Expo token and a development build.

### 5. Frame billing is unreachable from the UI

The engine fully supports per-frame pricing and frames-on-top, and the rules can be configured. But nothing in the session sheet lets a receptionist enter how many frames were played, so `frames_played` is always zero. A snooker club that bills by frame cannot use the app.

### 6. Screen-level test coverage is thin

The logic that matters most — billing, settlement, isolation — is heavily tested. But four of the most complex screens have no component tests at all, and there's no end-to-end run in CI. The flows were verified by hand against the real API, which doesn't protect against regressions.

### 7. Operational polish gaps

No receipt to hand a customer. No report export. No unread badge on the Alerts tab. Session history capped at 30 rows with no search. No "forgot password". Profile details can't be edited. None of these block a shift, but they'll all be asked for.

## What's left, in the order to do it

### 1. Onboarding — blocking

Club table management (create, rename, number, type, activate, maintenance status), staff management wired to `add_tenant_member`, and platform forms for creating a club and editing its branding and status. This is what turns the app from "works for the seeded club" into "works for a real customer".

### 2. Audit trail — cheap

A small `recordActivity()` helper called from the existing session, payment, pricing and stock mutations, plus a history view for owners. The table, policies and append-only grants are already in place.

### 3. Close the operational gaps

Frames entry on the session sheet, billing-rule editing in Settings, editable item quantities, expense edit/delete, past-day cash closings, and low-stock alerts actually being raised.

### 4. Notifications for real

A server-side worker reading `device_push_tokens` and sending via Expo, plus a development build. Needs an Expo account — the one item that can't be finished without credentials.

### 5. Equipment, receipts, exports

Equipment has schema and RLS but no UI. Receipts and report exports are the two things a club will ask for once it's running day to day.

### 6. Test the screens

Component tests for Cash, Reports, Manage and the session sheet, and an end-to-end run in CI so the flows verified by hand stay verified.

---

**Nothing on this list requires reworking the foundation.** Every item is additive — new screens over an existing schema, or wiring functions that already exist and already pass their tests. The database is complete for the whole product scope, not just what's on screen.
